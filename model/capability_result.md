> **Normative Standard**: This document is written in compliance with RFC 2119 normative syntax. Key words such as `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `MAY`, and `OPTIONAL` are to be interpreted precisely as described in BCP 14 (RFC 2119 / RFC 8174).
> **Constitutional Basis**: This canonical representation is directly derived from [abi/kernel_contract.md](file:///d:/ai-code-skin-mcp/rules-skill/abi/kernel_contract.md), the append-only authority model in [abi/ownership.md](file:///d:/ai-code-skin-mcp/rules-skill/abi/ownership.md), and the modular contract platform boundaries.
> **Transport Agnosticism**: This semantic model defines an abstract capability delivery output contract. It MUST NOT be coupled to concrete encoding formats, serialization conventions, or machine logging implementations.

## 1. Object Definition & Architectural Role

The `CapabilityResult` is the canonical semantic payload returned by an authorized Capability Driver upon finishing (or aborting) its assigned portion of an `ExecutionPlan`. It acts as the explicit operational boundary return contract, reporting state transformations back to the runtime kernel while preserving strict causality lineage.

### 1.1 Core Constitutional Invariants
1. **Strict Separation of Output vs. Side-Effects**: To prevent architectural confusion between abstract analytical findings and physical modifications to target resources, an conforming `CapabilityResult` MUST separate structural content into two mutually exclusive semantic domains:
   - **`output_payload`**: Pure analytical evaluations, proposed code patches, diagnostic findings, or reasoning syntheses.
   - **`side_effects`**: Explicit registrations of physical modifications performed (e.g., files created/modified, database schemas altered, system artifacts deposited).
2. **Exclusion of Verification Concerns**: A capability driver emitting this result SHALL NOT embed comprehensive CI testing outcomes, linting validity assertions, or compilation pass/fail verdicts directly into this model. Those concerns are strictly reserved for external automated validation pipelines utilizing `verification_result.md`.
3. **Append-Only Production**: As enacted in `ownership.md`, an executing driver acts strictly as an append-only producer of this result. Once transmitted back across the Agent Boundary Interface, the result payload CANNOT be retroactively modified or redacted by the originating capability.

## 2. Canonical Semantic Attributes

An conforming `CapabilityResult` SHALL contain the logical semantic attributes detailed in the table below:

| Semantic Attribute | Logical Domain Type | Required / Optional | Constitutional Constraint & Semantic Definition |
| :--- | :--- | :---: | :--- |
| **`result_id`** | Universally Unique Identifier | **REQUIRED** | Immutable unique identity coordinate. Required for causality lineage tracing in `EvidenceRecord`. |
| **`executed_plan_id`** | Universally Unique Identifier | **REQUIRED** | Mandatory causality pointer referencing the originating `ExecutionPlan` that initiated driver invocation. |
| **`originating_driver_id`** | Structured Namespace String | **REQUIRED** | Explicit signature identifying the exact capability driver manifest and trust level responsible for execution. |
| **`completion_status`** | Finite Enumeration | **REQUIRED** | Final task disposition. MUST be exactly one of: `SUCCESS`, `PARTIAL_COMPLETION`, `ABORTED`, or `POLICY_BLOCKED`. |
| **`output_payload`** | Structured Content Container | **REQUIRED** | Pure data syntheses, proposed diff structures, or analytical responses generated by the driver. |
| **`side_effects`** | Collection of Action Manifests | **REQUIRED** | Explicit record of physical changes applied across system resources, filesystem boundaries, or memory containers. |
| **`verification_reference_ids`** | Collection of UUID Pointers | **OPTIONAL** | References pointing to exterior verification checks or automated test runs scheduled to validate these side-effects. |
| **`contract_version`** | Semantic Version Identifier | **REQUIRED** | Declares the active Kernel ABI contract version under which this delivery payload was formatted. |

---

## 3. Normative Validation & Verification Rules

1. **Mandatory Side-Effect Transparency**: If an executing driver performs any alteration to filesystem content, environment variables, or repository state, every modified resource target MUST be explicitly enumerated within `side_effects`. Concealing physical changes outside `side_effects` is a critical boundary security offense that SHALL trigger immediate capability trust revocation.
2. **Policy Blockage Compliance**: If driver execution is halted prematurely due to exceeding budget ceilings or encountering forbidden guardrail zones, `completion_status` MUST be set to `POLICY_BLOCKED`, accompanied by diagnostic evidence clarifying the exact threshold that precipitated termination.
3. **Imparted Lineage Binding**: Any downstream evaluation or audit event evaluating the outcome of a capability run MUST link directly to `result_id` as part of its contiguous causality chain.
